## Lifecycle contract

Use a small private state machine inside the existing Razorpay service, not a global store or a second payment framework. Separate checkout lifetime, last attempt error, verification state, and disposal. Attempt errors are not terminal outcomes.

| State/event | Required behavior | Navigation |
| --- | --- | --- |
| Initializing | One order creation per submission; page remains busy | None |
| SDK load/order creation/checkout open fails | Deliver one initialization failure with honest error context; dispose any created checkout | Failure page or established explicit initialization error UI |
| Checkout open → `payment.failed` | Normalize and retain the most recent attempt error; keep checkout active and submit disabled | None |
| Checkout open → subsequent attempt failure | Replace the retained attempt error; do not settle or create an order | None |
| Dismissal with no failed attempt | Settle once as cancellation and release the busy state | Stay on payment page |
| Dismissal after failed attempt(s) | Settle the local checkout once using the latest attempt error, after dismissal; this is not proof that the server order can never later authorize/capture | Failure page once, with honest status wording |
| Payment handler starts | Enter verifying before awaiting any request; clear obsolete attempt error; ignore duplicate handlers and dismissal callbacks | None while verification is in flight |
| Server verifies and activates | Settle once as verified success; checkout must no longer cover the destination | Success page once |
| Server verification rejects | Preserve original payment proof and surface unresolved verification; never offer a new payment as recovery | Subject to D1; never treat this as a new failed attempt |
| Late event after terminal outcome | Ignore; cannot reset busy state, log another terminal failure, or navigate | None |
| Route unmount while initialization/checkout is active | Invalidate callbacks before closing the checkout; prevent a delayed order response from opening it | None |

Single-terminal-outcome means one of success, failure, cancellation, or the proposed verification-required outcome. It does not mean suppressing subsequent attempts while the existing checkout remains open. A terminal guard must therefore not be set in the `payment.failed` listener.

Return an explicit disposal handle from initiation and use a synchronous page ref to exclude double submissions. Separate disposal (resources/callback lifetime) from settlement (one local checkout outcome), so a success-triggered route cleanup cannot dispatch a second outcome or cancel an already-started server mutation. Account for unmount before the async initiation call returns: mark the page disposed immediately, suppress route/state effects, and dispose the eventual handle; also give the service a cancellation signal checked after each initialization await so it cannot open checkout on an abandoned route. Register React cleanup once and do not let ordinary renders dispose an active checkout. Cleanup must be idempotent and set the service disposed flag before calling SDK `close()`, because that call may trigger dismissal synchronously.

Recreate/reset the page cancellation controller correctly under React StrictMode effect setup/cleanup replay; never reuse an already-aborted signal for a later user submission. Tie the active checkout to the initiating authenticated user and invalidate it on logout/user change as well as route unmount. A subsequent user must not receive the prior user’s callbacks or proof. Do not infer verified identity from route state.

If verification has started, teardown can suppress browser callbacks but must not assume it canceled a server mutation or reversed a captured payment. Keep server activation authoritative. Do not install a global navigation blocker in this patch.

### Phase 4 — Repair diagnostic truthfulness and persistence

Own [paymentVerificationService.ts](../src/features/subscription/api/paymentVerificationService.ts), [log-error.ts](../functions/api/log-error.ts), failure-page logging integration, and proposed tests `src/features/subscription/api/paymentVerificationService.test.ts` and `functions/__tests__/log-error.test.ts`.

2. Reuse the existing authenticated endpoint and SSO client directly. Do not call the shared logger's localStorage retry path. Audit existing callers before removing request fields; accepting an old body field must never let it override authenticated identity.
3. Replace the stub so `logged: true` requires a successful durable-write response. Network, HTTP, body-envelope, and database failures must return an explicit unsuccessful logging result. Diagnostics never update payment/subscription transaction status.
4. Capture allowlisted code/reason/source/step, order/payment references, plan identity, and lifecycle stage. Keep the full actual order/payment reference available to support; the current page only displays the last 12 characters and fabricates `REF-<time>` when no gateway reference exists. Record amount units explicitly if an amount is included; do not substitute zero for an unknown amount. Bound and sanitize gateway descriptions. Exclude payment signatures, credentials, phone/email, card/UPI details, and raw SDK responses.
5. Log at a deliberate lifecycle event boundary, not a render-dependent effect. Select the service as the sole owner for recording each normalized failed-attempt event and the final local checkout outcome. Use distinct event types and an in-memory event identity to avoid counting a final dismissal as another failed attempt; repeated attempts may each be recorded. These are client-reported diagnostics, never authoritative payment/transaction status. Duplicate SDK events, re-renders, StrictMode, cancellation, and already-disposed callbacks must not duplicate a logical event. Bind the request to the initiating user; do not read a newly signed-in user from a global store and attribute the old user’s failure to them. Remove the failure page's duplicate write if event ownership moves to the service. Verify re-renders and late events cannot duplicate terminal diagnostics; browser reload deduplication across sessions is not claimed. Do not introduce a database unique constraint or durable deduplication mechanism without a separate design.
6. Logging failure remains separate from the payment outcome and is truthfully available to the caller/support diagnostics. Do not await a diagnostic network response before allowing checkout lifecycle handling or navigation; explicitly handle the rejected/failed result so there is no unhandled promise rejection. This is failure reporting, not permission to invent a substitute sink or successful log result; do not convert payment success into failure. No queue, alternate sink, automatic logging retry, or silent fabricated success is approved. If a new degraded logging policy is proposed, obtain D2 approval first.

Phase 4 is required to close the diagnostic findings, but is not a prerequisite for the narrowly scoped modal/navigation fix. Any split delivery must explicitly report this phase's status rather than claim the full remediation is complete.
